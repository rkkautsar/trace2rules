# trace2rules — architecture

## Goal

Turn coding-agent sessions into a small set of repository-specific `AGENTS.md` proposals backed by measured evidence.

## Pipeline

```text
source adapter
  -> canonical Session / ToolCall
  -> DuckDB sessions + tool_events
  -> detectors (hotspots, recovery loops, context blasts)
  -> exact sequence mining + lift / paired rework
  -> gated findings
  -> Markdown report prompt
  -> stdout
```

## Sources

| Format | Adapter | Notes |
|---|---|---|
| `swe-rebench` | `ingest/` | OpenHands-style parquet, cached locally from Hugging Face |
| `swe-chat` | `sources/swe_chat.py` | Optional example corpus; normalized `sessions.parquet` + `conversations.parquet` |
| `agent-trajectory` | `sources/agent_trajectory.py`, `sources/opencode.py` | Claude Code, Codex, Pi, OMP, and OpenCode SQLite/JSON |

`agent-trajectory` is a base dependency; Claude Code, Codex, Pi, and OMP still require Node.js 20+ at runtime. OpenCode SQLite ingestion is pure Python.

## DuckDB

`sessions` stores one row per session:

```text
session_id, repo, instance_id, resolved, total_turns,
source, agent, success_score
```

`session_id` identifies one agent run. `instance_id` identifies the user task: title-preserving continuation chains and subagent transcripts share the parent task.

`tool_events` stores normalized tool calls:

```text
event_id, session_id, repo, step_idx, segment_idx,
tool_name, action_type, verb, object_id, target, raw_target,
outcome, exit_code, error_signature, is_error,
approx_out_tokens, obs_excerpt
```

`segment_idx` is the compaction episode within a session. It is extracted from the raw transcript for Claude Code, Codex, Pi, and OMP; windows never cross a segment boundary. Local ingest splits compaction segments into separate sessions by default.

`write_sessions()` replaces rows by `session_id`, so re-importing a session is idempotent.

## Evidence

- Setup failures: repeated missing-import / editable-install patterns.
- Same-error loops: repeated exception signatures across edits.
- Hotspots: read-only files or paths touched across many sessions.
- Context blasts: commands or reads averaging large output.
- Exact sequences: recurring 3–5-step windows with support, lift, and paired-rework evidence; windows never cross a compaction boundary, and nested windows are deduplicated before reporting.

Generated verifier scripts and low-support task-specific sequences are filtered before reporting.

## Output constraints

Per repository:

- at most 10 rules by default;
- at most 160 lines;
- at most 12,000 characters.

Rules are generated by the user's coding agent from the Markdown report prompt; trace2rules makes no LLM calls.

## Non-goals

- Automatically editing a real `AGENTS.md`.
- Reconstructing tool execution that the agent never records.
- Committing datasets or generated proposal files.

## Data and privacy

Session data stays in the configured DuckDB file (`$TMPDIR/trace2rules/trace2rules.duckdb` by default). Downloaded datasets, generated proposals, and secrets are gitignored. trace2rules makes no external LLM or labeling calls.
